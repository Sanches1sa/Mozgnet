# MAX на другой платформе, ИИ и приложение — из одного облака

Это обновление не переносит бота в другую платформу автоматически: её название и API неизвестны. Оно предоставляет готовое мини-приложение, API облака и серверные адаптеры подключения. Бот продолжает получать события и отправлять сообщения средствами той платформы, на которой он работает.

## Адреса

Все компоненты обслуживает один процесс облака на одном IP/порту:

| Назначение | Адрес |
|---|---|
| Мини-приложение MAX | `https://ВАШ-АДРЕС/max-app` |
| База OpenAI-совместимого API | `https://ВАШ-АДРЕС/api/v1` |
| Ответ в формате OpenAI | `POST /api/v1/chat/completions` |
| Ответ поддержки с кнопкой заявки | `POST /api/v1/support/ask` |
| Заявки для платформы | `GET/POST /api/v1/support/tickets` |

Для серверного вызова из локальной сети допустим `http://IP:8077`. Для настоящего запуска мини-приложения в MAX нужен доступный ему HTTPS-адрес. Частный адрес 192.168.x.x не доступен телефонам за пределами этой сети. Домен может указывать на тот же один IP облака; отдельное облако для приложения не требуется. Порт фактически работающего облака может отличаться от 8077, если он был занят.

Пример обратного прокси Caddy, если он используется на вашем сервере:

```caddy
cloud.example.ru {
    reverse_proxy 127.0.0.1:8077
}
```

Домен, DNS, сертификат и регистрацию приложения в MAX необходимо настроить в вашей инфраструктуре. Обновление не публикует сервер само.

## 1. Настройки облака

1. Сделайте резервную копию приложения и каталога data. Установите ZIP и перезапустите облако.
2. Откройте настройки → «Приложение поддержки».
3. Впишите основной адрес облака, например `https://cloud.example.ru`, без `/api/v1` и `/max-app`.
4. Создайте ключ для другой платформы и сохраните его в секретах её сервера. Полный ключ показывается один раз. Это ключ приложения `n12-…`, не токен бота MAX и не пароль удалённого Ассистента.
5. Если платформа должна читать все заявки пользователей приложения, менять их статусы и получать временные данные удалённой поддержки, назначьте этот ключ «Ключом специалиста». Обычный ключ ИИ не имеет этих полномочий: он видит только заявки своего пространства пользователей.
6. Укажите токен того бота MAX, к которому будет привязано мини-приложение. Он нужен для серверной проверки подписанного запуска; это поле не включает получение событий MAX.
7. Если тот же бот работает на другой платформе, выключите встроенный получатель MAX в облаке кнопкой в этой вкладке. Два получателя одного токена могут конкурировать. ИИ API продолжает работать.
8. Сохраните настройки. Скопируйте адрес API и ссылку приложения.

Не используйте встроенный polling-бот облака как вторую копию внешнего бота. Внешняя платформа сама управляет своим webhook/polling. Существующий webhook другой платформы обновление не изменяет.

## 2. Подключение ИИ к платформе

Если платформа умеет OpenAI-совместимые подключения:

- Base URL: `https://cloud.example.ru/api/v1`
- API key: созданный в облаке ключ приложения `n12-…`
- Model: `mozg-12`
- Streaming: выключен (`stream=false`)
- Endpoint: `/chat/completions` относительно Base URL

В запросе `messages` передавайте историю именно нужного диалога. `mode=cloud` можно указать дополнительным полем; режим по умолчанию также использует общий облачный движок. Отдельные функции сторонних LLM, включая function calling, не реализованы этим API. Не направляйте обычные вопросы на `/api/think` или устаревшие маршруты LLM: используйте публичный API приложения.

Если платформа позволяет добавить серверный обработчик, используйте готовые файлы:

- `integrations/cloud_client.py` — стандартная библиотека Python, без дополнительных пакетов.
- `integrations/max_platform_adapter.mjs` — Node.js 18+, готовая функция для существующего обработчика сообщений.
- `integrations/cloud.env.example` — имена двух переменных окружения.

Для этих адаптеров `NEURO_CLOUD_URL` — только основной адрес, **без `/api/v1`**. `NEURO_CLOUD_API_KEY` хранится в секретах платформы. Адаптер не создаёт второго MAX-получателя. Его нужно вызвать в ИИ-ветке уже существующего обработчика платформы после локальных команд/сценариев заявок. Функция отправки сообщения передаётся от вашей платформы. Без её названия нельзя указать точное название меню или программно установить обработчик.

Серверный запрос поддержки:

```http
POST /api/v1/support/ask
Authorization: Bearer <КЛЮЧ ПРИЛОЖЕНИЯ>
Content-Type: application/json
```

```json
{
  "question": "Не открывается почтовый сервис. Что проверить?",
  "user_id": "12345",
  "session": "max:67890"
}
```

Возвращаются `answer`, `parts`, `engine=cloud-dialog`, `sources`, признак `unanswered` и `actions` со ссылкой «Подать заявку». Передавайте готовые `parts` пользователю, не заменяя их ответом локальной LLM платформы. Кнопку из `actions` сопоставьте кнопке URL/мини-приложения платформы. Разные пользователи и чаты должны иметь разные `user_id`/`session`.

Обычный `POST /api/v1/ask` с `mode=cloud` также доступен. Интернет зависит от настроек облака и доступности настроенного поискового API. Обращение к правильному API не создаёт знаний, которых нет в модели и источниках. Если решения нет, профиль поддержки предлагает уточнить сервис/ошибку или подать заявку, а не выдаёт «нет подтверждённой памяти» за полезный ответ.

## 3. Приложение MAX

В кабинете MAX привяжите к тому же боту URL `https://cloud.example.ru/max-app` по правилам платформы. В интерфейсе пользователя будут:

- форма заявки: сервис, описание, контакт;
- поля программы удалённой поддержки «Ассистент»: идентификатор и временный пароль, показ/скрытие, отдельное копирование и копирование пары;
- чат с общим ИИ облака;
- свои заявки и их статусы;
- перенос нерешённого вопроса в форму заявки.

Из MAX отправляется исходная строка `initData`; сервер проверяет HMAC, уникальность параметров, время и пользователя, затем выдаёт часовую сессию приложения. `initDataUnsafe` не используется для доверия. Токен MAX и ключ приложения не встраиваются в публичный JavaScript. Проверка подписи основана на официальной документации:

- https://dev.max.ru/docs/webapps/validation
- https://dev.max.ru/docs/webapps/bridge

В обычном браузере без запуска из MAX приложение не получает доступ к данным пользователя. Специалист может войти в панель облака и открыть `/max-app`: он увидит все заявки, кнопки копирования и изменение статуса. В MAX посторонний пользователь видит только свои обращения. Смена токена MAX отзывает старые сессии и меняет пространство пользователей; прежние заявки остаются доступны специалисту.

## 4. Что происходит с заявкой

Форма действительно создаёт запись в `data/support_tickets.json` и выдаёт номер `REQ-…`. Первоначально доставка — `cloud`: «Сохранена в облаке». Это не подтверждение регистрации в неизвестной внешней системе.

Платформа с назначенным ключом специалиста может забирать заявки:

```http
GET /api/v1/support/tickets
Authorization: Bearer <КЛЮЧ СПЕЦИАЛИСТА>
```

После создания заявки в своей системе она должна прислать реальный внешний номер:

```json
{
  "action": "update",
  "id": "REQ-НОМЕР",
  "status": "in_progress",
  "external_id": "НОМЕР_ИЗ_ДРУГОЙ_ПЛАТФОРМЫ"
}
```

Тогда доставка изменится на `external`, и пользователь увидит номер платформы. Допустимые статусы: `new`, `in_progress`, `resolved`, `closed`. При закрытии временный пароль удаляется.

Создать запись через API можно POST-запросом с `service`, `description`, `contact`, `user_id`, необязательными `remote_id`, `remote_password` и `request_id`. Стабильный `request_id` защищает от повторного создания при повторной отправке. Обычный ключ может работать только со своим пространством заявок; назначенный ключ специалиста имеет доступ ко всем. Не размещайте его в браузере пользователя.

Для временного пароля нужен отдельный авторизованный POST:

```json
{"action":"reveal","id":"REQ-НОМЕР"}
```

В списках пароль отсутствует. Доступ разрешён владельцу обращения и специалисту. Ответ с паролем помечен `Cache-Control: no-store`.

## 5. Данные удалённой помощи

Идентификатор хранится отдельным полем обращения. Пароль хранится только в оперативной памяти процесса, максимум 2 часа. Он теряется после перезапуска облака. В файл заявок, журналы приложения и ИИ-контекст поле пароля не передаётся. Копирование выполняется по нажатию пользователя или специалиста. При недоступности буфера обмена приложение сообщает об ошибке, не заявляя ложное «скопировано».

Необходимые ограничения: пароль после истечения срока надо запросить у пользователя заново; это не долговременный сейф. Поля, специально введённые пользователем в текст описания или вопроса, являются обычным текстом — автоматического распознавания секретов внутри произвольного текста нет.

## Проверка и границы готовности

Проверены модульные сценарии подписи, подмены, срока запуска, разграничения пользователей и ключей, идемпотентности, хранения/истечения пароля, изменения статуса и отсутствия пароля в ИИ-вызове. В Chromium через реальный HTTP проверены мобильная форма, копирование, заявка, чат, перенос вопроса, защита от чужого пользователя и сохранение настроек. MAX SDK и запуск подменены тестовым подписанным запуском; настоящие сообщения в MAX не отправлялись.

Регистрация в кабинете MAX и установка адаптера в другой платформе не выполнены: доступа к кабинету и API платформы нет. Новый интерфейс не проверяет автоматически состояние внутренних сервисов организации и не выдумывает такие проверки.
